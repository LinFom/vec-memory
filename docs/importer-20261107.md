# 票 02 — 第一个离线导入器样例 [by:WorkBuddy]

日期：2026-11-07 · 分支 `feat/memory-interop-rerank` · 入口 [`tools/import-contract-document.mjs`](../tools/import-contract-document.mjs) · 源侧 [`interop/importers/`](../interop/importers/README.md)

## 0. 做了什么

两段式、都以离线为主：

1. `interop/importers/jsonl-to-contract.mjs`：把任意第三方 Agent 导出的 `facts / people / events / anchors` 四类 JSONL（加可选 `messages.jsonl`）转成 `vec-memory/import@1` 契约文档。字段名与映射表全在 `interop/import-mapping.json`，**不含任何整合包专名**。
2. `tools/import-contract-document.mjs`：校验契约 → 生成**确定性**导入计划 → 可选提交。默认不发任何请求，`--submit` 才走服务 v1 已有的 `/entities`、`/messages`、`/memories`、`/workspace`。

样例数据在 `interop/examples/legacy-jsonl/`（4 类各 1 行 + 2 条 user 原话）。

## 1. 关键决策（用户授权「按专业通用思想决定」）

| # | 决策 | 依据 / 代价 |
| --- | --- | --- |
| I1 | **不新增 HTTP 端点**，只复用公开 v1 路由 | 新增写入口会变成第二个事实来源；票 01 契约是离线 JSON 文档，不是接口 |
| I2 | **不伪造服务字段**：服务没有条目级 `verified`，就不往正文塞标签 | 未核验由三重证据保证：契约 `origin.verified=false`（`const:false` 锁死）、`/workspace` 的 `legacy:true + confirm:false`（服务端落 `candidate`）、导入结果逐条 `unverified:true` |
| I3 | 台账 `text` 用占位描述，**不复制原话正文** | 票 07 红线：原文只在 `messages.jsonl` 存一份；完整来源靠 `legacyRecord.origin.source.locator` 回查。占位文本含 entry.id，保证 `scene-memory` 的 signature 唯一 |
| I4 | 幂等 = 稳定 `operationId`（`sha256(spaceId, entry.id, locator)`）+ `messageId` | 服务端自带 replay / duplicate 判定；失败不回滚、不写本地游标，重跑同一文档即续上 |
| I5 | `scope.kind` 的 `game` / `channel` 显式收窄为 `group`，`id` 原样保留 | 服务 v1 只认 private/group；映射表写清，不静默改写 |
| I6 | 缺 `actorId` ⇒ 隔离，不登记实体、不写事实记忆 | 对齐票 07 / D11 与既有 `quarantineUnattributedEvidence`；若还想挂 `subject.kind=person` 直接 `UNATTRIBUTED_PERSON` 拒绝 |
| I7 | 台账走 `/workspace`，需要管理员凭据 | `scene-memory.entry()` 的 `legacy/confirm/shareable` 仅 admin 生效；非管理员会静默丢标记，所以工具明确要 admin token 并在 README 写清 |
| I8 | `source:'manual'` 写入 `/memories` | 历史导入不是模型生成，且 `source!=='manual'` 会强制 evidence 的 `role=user` 与同场合校验；`manual` 仍保留 `evidenceIds` 回指，不丢证据链 |

## 2. 实测结果（真实 HTTP 服务，非 mock）

`node --test test/import-contract-document.mjs` → **8 pass / 0 fail**。测试用 `initialize(root)` + `createStandaloneServer({root})` 在临时目录起真实 standalone 服务，创建 project + 三个 space，逐项验证：

| 验收项 | 状态 | 证据 |
| --- | --- | --- |
| 四类来源都有字段映射、映射表逐项可核 | ✅ | `mapping` 4 条 → `preference / speaker_profile / event / topic`；`interop/import-mapping.json` + importer README 表 |
| 导入幂等，重跑不产生重复条目 | ✅ | 第二次提交 4 条 memory 全 `replayed:true`；`/workspace state` 台账条数不翻倍 |
| 导入后 recall 能命中 | ✅ | `POST /recall` 的 items 含「不加糖的茶」 |
| 带「历史导入 / 未核验」标记 | ✅ | 4 条台账全 `legacy:true` + `status:'candidate'` + `legacyRecord.unverified:true`；契约 `verified:false` |
| 不依赖服务内部模块、不写生产库指针 | ✅ | 源码断言零 `src/` import、零 `vector-active.json`；四个真值层文件相对 `c06e8fe` 的 `git diff` 为空 |
| 人格/情绪运行态不导入 | ✅ | 构造含 `persona/emotion/embedding/confidence` 的 JSONL ⇒ 契约里零命中，审计清单列出 4 项 |
| 失败可读且不留下半导入状态 | ✅ | 第 5 个请求注入断网 ⇒ `ImportSubmitError('IMPORT_NETWORK')` 带 `completed:[4 步]`；重跑同一计划成功，台账 4 条无半状态 |
| `src/core/*` 与 `src/standalone/*` 零改动 | ✅ | 本票新增/修改的文件全在 `interop/`、`tools/`、`test/`、`docs/`；四个真值层 diff 为空（同分支票 04/07 对 `src/` 的改动属于各自票，不计入本票） |

离线链路 CLI 冒烟：`4 entries / 2 messages / 4 unverified / 11 steps`，两次生成的计划 JSON 逐字相同。

## 3. 诚实局限

1. **没有人工核对队列 UI**：台账是后端数据，界面仍缺，见 `docs/TODO-human-review-page-20261107.md`（08 号登记票，前端由用户侧负责）。本票只保证队列的**数据源**存在。
2. **服务不裁决矛盾陈述**：同一主体在不同来源的矛盾说法按场合并列保存、各自带来源引用，不会被自动合并（与 D9 一致）。
3. **`game`/`channel` 场合信息有损**：收窄为 `group`，只在 `scope.id` 里保留原标识；要保留独立场合语义得先扩服务协议。
4. **需要管理员凭据**：非管理员调用 `/workspace` 时 `legacy/confirm` 会被服务端忽略，标记静默丢失 —— 这是既有服务语义，工具没有偷偷补写。
5. **只接了 JSONL 一种源形状**：别的项目要接，改 `import-mapping.json` 的 `sourceFiles` / 字段映射即可；契约本身不绑定这个形状。
6. **未核验不参与评分权重**：`origin.verified` 只是来源属性，不进召回打分；要改须另开 ADR + 真库校准（`docs/decisions-20261107.md` D6）。
