# 项目客观评估（2026-11-01）

- 评估对象：vec-memory 当前仓库源码、测试、协议、评估 JSON
- 目标版本：0.32.0
- 评估立场：个人自托管工具，不是成熟 SaaS，不宣称生产全验证
- 方法：以实际代码路径和测试断言为准；目标选择与实现差距分开写；没有数字证据的地方不编数字

## 0. 结论

0.32.0 解决的是“把记忆从宿主插件变成一个可独立部署、可认证、可备份、可人工纠正的服务”，而不是“把记忆做成数据库/云服务”。

已经成立的：

- 独立服务可以初始化、启动、创建项目/空间，经 `/api/v1` 使用；
- 空间 owner/readers 权限、共享读取、采用时复核有实际代码和测试；
- 默认不自动调用生成模型；
- 场景、人物人工修订、账号绑定、主体观察都有明确的数据路径；
- 完整/空间备份、密码校验、损坏检测、旁置恢复、空间替换 rollback 有实现和测试；
- 固定 6 条合成案例的 hard 阈值改动有前后 JSON。

不能宣称的：

- 不能宣称“已完全脱离宿主/没有兼容层”；
- 不能宣称“生产级认证/多租户/高可用/大型数据库备份”；
- 不能宣称“记忆内容正确/长期记忆优于其他产品”；
- 不能宣称“账号绑定后所有场合人物原话自动互通”；
- 不能宣称“撤回/纠正后历史误归属全部修复”；
- 不能宣称“所有任务任意步骤可续跑”；
- 不能把 6 条合成指标外推为真实 LLM 质量。

- 包、适配器和发布版本统一为 `0.32.0`；服务版本读取 `package.json`，避免独立常量漂移。

## A. 首宿主耦合

### A.1 旧问题

旧形态是 QQ-Agent 插件/宿主数据目录的一部分：认证、空间、身份、模型配置都依赖宿主；脱离宿主就没有完整入口。这个批评在 0.30 之前是成立的。

### A.2 本次设计

- `tools/standalone-server.mjs` 提供 `init`/`serve --root`，服务根、项目、空间、凭据由服务自己管理。
- 业务入口是 `src/standalone/service.mjs` 的 `handle`；HTTP 只是 `server.mjs` 的薄封装。
- 每个空间由 `src/standalone/worker.mjs` 承载，现有 `src/core/*` 引擎继续使用。
- 旧宿主目录只作为兼容读取/显式导入的来源，不是独立实例的运行前提。
- QQ 适配层变成薄 HTTP 客户端；协议 v1 队列在适配层持久化消息。

### A.3 实际证据

- `tools/standalone-server.mjs`：`init|serve --root`；默认 `127.0.0.1:8091`。
- `src/standalone/service.mjs`：`initialize(root)` 创建 `access.json`；`createService({root})`；`GET /api/v1/version` 报 `0.32.0`。
- `test/standalone-service.mjs`：临时根起服务、HTTP 401/200、空库工作流、重启后数据仍在。
- `test/standalone-upgrade.mjs`：临时根 `initialize` + `createService`，跑场景/人物/备份导入，不依赖 QQ 宿主。
- `adapters/qq-agent/protocol-v1.mjs`：`/api/v1/spaces/...`，持久队列，目标 base/space 变化拒绝。

### A.4 代价

- 为了兼容，worker 仍把 `legacy/data` 作为老引擎目录；空间目录里同时存在 `input/` 和新布局，理解成本高。
- `router.mjs` 仍保留旧 `/api/vec` 兼容实现；`adapters/qq-agent/index.js` 仍保留旧协议分支。
- 适配层默认 `serviceBaseURL=http://127.0.0.1:8088`，服务默认 8091；不手工对齐就会“服务正常但适配层连不上”。
- `tools/import-group-memory.mjs` 默认 URL 为 `http://127.0.0.1:8091`，可用 `VEC_MEMORY_URL` 覆盖；管理凭据用 `VEC_MEMORY_ADMIN_TOKEN`。
- 服务版本已由 package.json 读取；适配器发布元数据仍需随版本同步。

### A.5 剩余欠账

- 把兼容层和独立路径的边界写进部署默认值（端口、版本、URL），最好由配置校验而不是文档记忆。
- 逐步把 `legacy/data` 命名/旧 `/api/vec` 从新接入路径中隔离，明确“仅兼容”。
- 保持适配器发布元数据与 package 版本同步；本次均为 0.32.0。
- 真实迁移验收：移走宿主目录后启动、导入、检索、回退，各跑一次。

### A.6 结论

**部分解耦成立，完全解耦未完成。** 独立服务是主路径；但“仓库里已经没有宿主耦合”是不准确的。

## B. 自有存储承担数据库职责

### B.1 旧问题

项目用 JSON/JSONL + 自定义向量文件承担事实、事件、场景、任务、收据等存储职责。没有数据库的查询、事务、并发控制、备份恢复能力，却要表现得像数据库。

### B.2 本次设计

- 单文件追加日志 `DurableLog`：hash 链、seq、previous、operationId/fingerprint、fsync、失败截断回滚、损坏只读。
- 场景整体状态一次 `workspace.jsonl` 提交；人物修订单独日志 + 读时投影；人物→场景用持久 intent。
- 向量代：`vector-generations/<id>`、`vector-active.json` 指针、`rebuild-job.json` 续跑、`put-pending.json`。
- 备份/恢复：归档校验、逐文件 sha256、JSON/JSONL/hash 链检查、新目录恢复、空间导入 intent/rollback。
- `audit` 在恢复/维护时检查日志、事实库、主体、lineage 可读性。

### B.3 实际证据

- `src/core/durable-log.mjs`：加载校验、`assertReadable`、`append` 的 fsync/ftruncate、operationId 幂等。
- `src/core/scene-memory.mjs`：`mutate` 单次 append 整个 state；`retract` 写 history；`link` 读时投影。
- `src/core/manual-revisions.mjs`：独立日志 + `records/project/readStore` 投影；`expectedEtag`。
- `src/core/vector-generation.mjs`：`rebuild-job.json`、代目录复用、继承计数、publish 指针。
- `src/standalone/backup.mjs`：512 MiB、safeName、sha256、journal chain、staging、auto tasks off、jobs failed。
- `test/standalone-upgrade.mjs`：加密完整/空间备份、错密码/损坏、不覆盖、service 导入。
- `test/standalone-service.mjs`：失败引擎不产生成功收据；重启后数据可读。

### B.4 代价

- 没有跨文件 2PC/事务；消息、事实、场景、手动修订、任务状态可能在不同文件里分步完成。
- 单写者锁：同一 root 只能一个进程；没有并发多主。
- 备份全内存构建/校验，512 MiB 上限，不是流式数据库备份。
- 恢复只做到 audit 级验证，不是全量语义校验；损坏/半完成仍需人工。
- 历史依赖缺失时无法自动还原；只能保留现状或人工处理。
- 版本升级/迁移需要显式导出、导入、回退，不是 `ALTER TABLE`。

### B.5 剩余欠账

- 明确每个跨文件流程的“可恢复状态机”，最好把 intent/recovery 写成统一机制，而不是每个流程各有一套。
- 增加断电/进程 kill 注入测试，验证每个窗口的恢复结果。
- 备份增加增量/流式/分卷方案，或明确“大库请用文件系统快照”。
- 提供只读一致性检查工具，把 `audit` 的边界写清楚。

### B.6 结论

**它仍是一个“带日志和恢复机制的文件存储”，不是数据库。** 对个人自托管、单写入者、可停写备份的规模是合理取舍；不能按数据库 SLA 评估。

## C. 入口模块浅而复杂

### C.1 旧问题

入口模块看起来薄，但内部藏了太多职责；路由、校验、兼容、模型、存储交织，接入者难以判断哪个是稳定契约。

### C.2 本次设计

- 分层：`server.mjs` 只做 HTTP/同源/大小限制；`service.mjs` 做认证/权限/管理/任务/备份；`worker.mjs` 做单空间业务；`src/core/*` 做引擎。
- 公开 API 固定 `/api/v1`；旧 `/api/vec` 不是新接入接口。
- HTTP 和进程内都走 `service.handle`，避免两套业务逻辑。
- 备份、场景、手动修订、向量代拆成独立模块，按事务边界组织。

### C.3 实际证据

- `src/standalone/server.mjs` 约 47 行；`service.mjs` 约 288 行；`worker.mjs` 约 228 行（行数只作结构参考，不是质量指标）。
- `server.mjs` 的 `service.handle` 调用；`test/standalone-service.mjs` 直接调用 `handle`，HTTP 测试也验证同一认证。
- `docs/standalone-protocol.md` + `openapi/standalone-v1.json` 提供契约；`service.mjs` 的 `capabilities` 列出主要能力。
- `src/router.mjs` 仍有约 190 KB 旧路由；新服务没有把它删掉。

### C.4 代价

- `service.mjs` 的 `handle` 仍是一个大分支：管理、空间、任务、备份都在一个函数里；新增路由容易继续堆。
- 运行时没有按 OpenAPI 做统一 schema 校验；很多字段靠各 handler 自己 `requireText`/判断。
- 错误映射比较粗：有 `status` 的错误返回具体信息，否则 500 统一成 `Internal service error`，排障要看日志/测试。
- UI 是一个 59 行的压缩单页，功能多但可维护性有限；没有组件化/前端测试。
- 兼容代码（`router.mjs`、旧 `/api/vec`、`legacy/data`）让“入口浅”只对独立服务成立，对整仓不成立。

### C.5 剩余欠账

- 把 `service.mjs` 的管理、空间、任务、备份拆成独立 handler 模块，保持 `handle` 只做分发。
- 用 OpenAPI 生成/校验请求 schema，至少覆盖写接口。
- 统一错误码表和 HTTP 状态映射，避免 500 吞掉可诊断信息。
- 浏览器烟雾检查已验证档案小卡与场景历史；后续把脚本纳入持续集成并覆盖更多修改流程。

### C.6 结论

**独立服务的入口比旧插件清晰，但整仓仍有“薄入口 + 大兼容层”的问题。** 这是可维护性欠账，不是功能缺失。

## D. 隐私宣称过度/认证缺失

### D.1 旧问题

旧文档容易把“占位符/不落明文/本地”说成绝对隐私保证；认证缺失时，任何能访问服务的人都能读写。这个批评现在仍然值得保留，因为“有 Bearer”不等于“生产级安全”。

### D.2 本次设计

- 所有 `/api/v1` 路由要求 Bearer；管理员/项目 token 只存 sha256 哈希。
- 管理员、owner、reader 分级；管理接口、场景管理、绑定、备份要求管理员。
- 浏览器请求同源检查；CSP；JSON 正文 4 MiB；备份上传 1 GiB。
- 设置读取不回显密钥，只返回是否配置。
- 备份支持密码加密（scrypt + AES-256-GCM）；完整备份包含凭据哈希和身份密钥。
- 人物读取用人工投影；场景共享只给摘要/证据受限。

### D.3 实际证据

- `src/standalone/service.mjs`：`principal` 哈希比较、`permit` owner/readers、admin-only 分支。
- `src/standalone/server.mjs`：Origin 同源、CSP、4 MiB 限制、上传密码走 header。
- `test/standalone-service.mjs`：无 token 401；项目访问别的空间 403；reader 写 403；settings 不回显 `private-key`。
- `test/standalone-upgrade.mjs`：完整备份不含明文 `secret`；错密码/损坏拒绝；空间备份不含 `llmApiKey`。
- `backup.mjs`：AES-GCM、scrypt、tag、checksum、路径安全。

### D.4 代价/仍需承认的事实

- **消息正文是明文落盘**：`input/messages.jsonl` 保存原始 text；占位符主要保护事实/索引文本，不等于整库加密。
- **模型调用会把内容发到你配置的端点**：整理/索引/查询向量化都可能出境；默认关闭自动任务只是不主动花钱，不是不出境。
- **空间备份默认可能未加密**：`createBackup(root,{spaceId})` 没有密码时是 `encrypted:false`；必须推荐设置密码。
- **完整备份包含身份密钥和模型密钥**：拿到备份 + 密码的人可以恢复出配置；备份文件要离盘保管。
- **没有内置 TLS/限速/暴力破解防护/token 轮换/吊销/审计日志**；远程部署依赖反向代理。
- **管理员 token 丢失后不能从备份恢复明文**：备份保存的是哈希，已有 token 继续有效，但不会显示原 token。
- **`/health` 无认证**，只返回存活；不要把它当权限接口。
- **密码下限只有 8 位**：这是最低门槛，不是强度保证；应使用长随机密码。
- **管理员是单角色**：没有细粒度 RBAC、没有按项目分配管理权限。

### D.5 剩余欠账

- 文档统一改成“消息明文、模型可能出境、备份需自行加密保管”的准确表述，删除绝对化隐私措辞。
- 加 token 轮换/吊销、管理员操作审计、登录限速。
- TLS/反代部署清单和失败模式写进操作文档。
- 对空间备份强制密码或至少在 UI 明确警告“未加密”。

### D.6 结论

**认证从“缺失”进步到“有 Bearer + 角色”，但隐私仍是“自托管边界内的工程保护”，不是绝对保证。** 不能回到“没有认证”的旧叙述，也不能宣称“生产级安全”。

## E. 记得牢未必对/排序自强化

### E.1 旧问题

“记得久/召回多”容易被当成“更正确”；排序可能因为被反复注入/采用而自我强化，形成“越常出现越靠前”的循环。

### E.2 本次设计

- 每条事实/事件/观察/场景条目尽量带来源；候选/观察/人工有状态区分。
- 场景重复内容不新增条目；重复证据不重复计数；撤回/纠正写墓碑。
- 人物人工值通过投影优先，机器再抽取不覆盖。
- 采用只证明“进入上下文”，不证明“模型使用/事实正确”。
- 事件排练有 30 分钟冷却；采用只对事件/文档计数，不直接给事实槽加分。
- query 时 hard 阈值减少无关偏好注入（6 条合成案例）。

### E.3 实际证据

- `src/core/scene-memory.mjs`：重复返回 `duplicate:true`；`retract` 写 `rejectedSignatures`/history；`authority` 人工保护。
- `src/core/manual-revisions.mjs`：人工投影 + `source_changed`；`readStore` 拒绝写。
- `src/core/factstore.mjs`：`slotCredibility = evidence_n × legacy 折减`（多值槽按条目计价）；没有“采用次数”直接进公式。
- `src/core/consolidate.mjs`：`bumpEventHits` 30 分钟冷却；`readHitLog` 聚合。
- `src/standalone/worker.mjs`：`adoption` 只对 `event:`/`document:` 做 `bumpEventHits`；`rehearsal` 返回。
- `test/standalone-engine.mjs`：采用 working 条目不会 bump，事件会 bump；机器消息不能支撑事实。
- `test/standalone-upgrade.mjs`：人物纠正后旧证据重抽，人工值仍为“红茶”。
- `docs/recall-evaluation-*.json`：before/after 指标。

### E.4 代价

- **事件排练仍影响保留/升长期**：越常被采用的事件越可能长期保留/更靠前，这是设计上的“排练”，但也可能放大早期偏好。
- **事实槽聚合是 evidence-max**：多条冲突说法不一定同时展示；证据更多的旧版本可能压过新版本（多值槽另有处理）。
- **hot/boost 排序**：query 时 hard 已降低无关注入，但无 query 的日常注入仍是 boost；可信度/新旧/场合仍会影响顺序。
- **没有语义真值判断**：系统不能判断“绿茶”是否真的比“红茶”正确；人工修订是主要纠错手段。
- **评估太小**：6 条合成查询只能说明这个 fixture 上 hard 阈值减少了误注入，不能说明真实 LLM 抽取、讽刺、长期优势或跨产品优劣。
- **采用计数会少计**：worker 重启丢内存收据；系统明确不补造，这是诚实但会低估使用。

### E.5 剩余欠账

- 给“排练→排序”的影响做可解释的衰减/上限，避免早期采用长期垄断。
- 为冲突事实提供“并列展示/来源对比”，而不是只靠 evidence-max。
- 扩大真实/半真实评估集，标注讽刺、反语、时间变化、人物纠正；不要只用 6 条合成。
- 把“采用≠正确”写进 UI 和 API 文档的显眼位置。

### E.6 结论

**“记得牢”与“记得对”已经分开建模，但排序自强化没有被消除。** 这是可接受的个人记忆工具取舍，不是准确率保证。

## F. 文档当前真值分散

### F.1 旧问题

README、协议、迁移说明、评估 JSON、代码注释各自有一套“当前行为”，版本/端口/能力容易互相矛盾。

### F.2 本次设计

- 新增四份 2026-11-01 文档：完整设计、客观评估、备份恢复、升级说明。
- 设计文档逐项标注“目标/实现/差距”；备份文档给出可执行命令和失败处理；升级文档给版本兼容与回退。
- 评估 before/after JSON 保留，不覆盖历史。
- 协议文档和 OpenAPI 继续作为 HTTP 契约；设计文档不复制所有字段，只解释边界。

### F.3 实际证据

- `README.md` 说“自动模型任务默认关闭”“独立服务”；与源码一致。
- `docs/standalone-protocol.md` 默认 8091；与 `tools/standalone-server.mjs` 一致。
- `adapters/qq-agent/index.js` 默认 8088，文件头 0.32.0；旧默认端口与独立服务 8091 不同，需显式配置。
- `tools/import-group-memory.mjs` 默认 URL 为 `http://127.0.0.1:8091`，可用 `VEC_MEMORY_URL` 覆盖；管理凭据用 `VEC_MEMORY_ADMIN_TOKEN`。
- 包、适配器和发布版本统一为 `0.32.0`；服务版本读取 `package.json`，避免独立常量漂移。
- `docs/recall-evaluation-before/after` 都有；指标与 `evaluate-memory.mjs` 口径一致。

### F.4 代价

- 文档不是运行时生成的，版本/端口/能力仍可能漂移；没有 CI 检查“文档引用的路径/命令是否存在”。
- 设计文档较长，接入者仍需先读协议；评估文档偏维护者视角。
- 旧文档（迁移、thing-memory）继续存在，读者要自己判断哪份最新；本次更新协议和接入说明，旧文档仍需逐步收口。
- 没有“文档覆盖测试”，不能防止下次改动后文档过期。

### F.5 剩余欠账

- 把版本号、默认端口、能力列表收敛到单一来源（例如构建时注入或配置常量），文档引用它。
- 加一个文档检查脚本：引用路径存在、CLI `node --check`、示例 JSON 可解析。
- 旧文档加“最后核对日期/适用版本”，避免与 0.32.0 混淆。
- 发布流程要求更新 README/协议/升级说明，而不是只改代码。

### F.6 结论

**文档比之前集中，但“单一真值”还没有工程化保证。** 服务版本已收敛到包版本；文档仍需人工核对，适配器保留旧端口默认值，需要显式配置。

## G. 综合判断

### G.1 适合的定位

- 个人/小团队自托管，单机、单写入者、可停写备份；
- 需要证据、人工纠正、场景档案和可审计日志，但不需要数据库级事务/SaaS 多租户；
- 能接受“模型质量未验证、需要自己配置和验收”。

### G.2 不适合的定位

- 直接对外提供多租户 SaaS；
- 要求高可用、在线扩容、跨地域容灾；
- 要求 512 MiB 以上库的在线流式备份；
- 要求“绑定账号后所有场合人物原话自动互通”；
- 要求“记忆内容自动保证正确”。

### G.3 建议的验收顺序

1. `node --check` 所有引用的 CLI/模块。
2. `node --test test/standalone-upgrade.mjs`、`npm test`、`npm run test:adapter`（以当前代码实际结果为准，不引用会变的总数）。
3. 临时根初始化服务，创建项目/空间，提交消息/事实/场景，跑 recall/adoption。
4. 完整备份 + 错密码/损坏 + 空间导入 + 完整恢复旁置目录；验证失败不切换。
5. 停写导出、回退演练；确认新增消息/人工操作不会因切回旧目录丢失。
6. 管理页逐项点击：场景/人物/绑定/备份预览。
7. QQ 适配层对齐 8091/0.32.0 后做一次真实宿主联调；没有这一步，不宣称“适配完成”。

### G.4 总表

| 旧问题 | 本次设计 | 实际证据 | 代价 | 剩余欠账 |
|---|---|---|---|---|
| A 首宿主耦合 | 独立服务 + 空间 worker + HTTP | 服务/测试/迁移工具 | legacy 目录、旧路由、端口不一致 | 完全解耦、配置统一 |
| B 文件存储当数据库 | 日志/代/备份/intent/audit | DurableLog、backup、vector-generation | 无跨文件事务、512 MiB、单写者 | 状态机、断电测试、增量备份 |
| C 入口浅而复杂 | server/service/worker 分层 | server 薄、service.handle、协议 | 大 handle、无运行时 schema、兼容层 | 拆 handler、schema 校验 |
| D 隐私/认证 | Bearer + 角色 + 同源 + 加密备份 | 401/403、密钥不回显、备份测试 | 无 TLS/限速/轮换；消息明文；空间备份可未加密 | 安全加固、准确措辞 |
| E 记得牢≠对 | 证据/候选/人工/墓碑/采用分离 | scene/manual/adoption/eval | 排练影响排序、evidence-max、评估小 | 衰减、冲突展示、真实评估 |
| F 文档真值分散 | 四份新文档 + 保留 before/after | 文档/JSON/源码对照 | 版本/端口漂移、无 CI | 单一来源、文档检查 |

### G.5 最终结论

0.32.0 的核心价值不是“更会记”，而是“记忆的来源、权限、失败和恢复边界更清楚”。它已经可以作为个人自托管服务使用，但必须带着以下前提：

- 单机、单写者、可停写；
- 认证有了，但安全加固要自己做；
- 备份有上限，恢复要人工切换；
- 人工纠正是主要纠错手段；
- 评估只到合成关键词语义检索，不外推生产质量；
- 版本/端口/适配层还没完全收口。

按这个边界使用，它是诚实可维护的工具；越过这个边界宣称成熟 SaaS/生产全验证，就是不准确的。
