# 第三人称人物回忆与自动印象线索（0.32.1）

- 状态：0.32.1 补丁说明与设计记录
- 日期：2026-11-01
- 范围：自动人物印象、第三人称提及、转述来源、跨场合档案边界、QQ 适配层提示词
- 验证口径：临时记忆库、合成聊天记录与模拟整理模型，不调用外部付费模型；没有真实 QQ 对话调用率数据。

## 1. 一句话说明

自动注入阶段只给人物信息最多 2 条关键词线索，不再整卡铺开；显式工具查询用 `purpose:"query"` 走完整检索。A 谈 B 时 B 不必在场或发言；只按无歧义稳定身份识别，B 的档案保留 A 的转述来源，不写成 B 自述。跨渠道原话仍不开放，新空间默认同场合，管理员显式保存档案共享设置后才按既有规则读取。

## 2. 自动注入与显式查询

| 入口 | `purpose` | 人物信息行为 |
|---|---|---|
| QQ 自动注入、独立协议自动召回 | `automatic` | 人物 `semantic` / `profile` 合计最多 2 条；按字段取线索，关键词匹配；其余层不受这 2 条限制 |
| `memory-vec__search` 等显式查询 | `query` | 走完整召回；可拿更多人物字段与来源，但仍受既有条数、可见性和场合限制 |

- 上限是“整个自动请求的人物层合计最多 2 条”，不是每个人 2 条，也不是所有层合计 2 条。
- `semantic` 与 `profile` 共用这 2 个名额；候选先按 `who + line` 做关键词重合度打分，只保留有命中的，再按分数和可信度排序。
- `profile` 以单个字段（`k=v`）为候选，不把整张人物卡拼成一条；字段级来源优先取该字段的 `itemProvenance`。
- 自动路径不为了人物线索调用 embedding，人物层按关键词处理；事件、长期语料、主体、工作记忆、场景等其他层照常追加，因此整个注入块的总条数仍可能超过 2 条。
- 显式查询不受这 2 条上限约束，但仍受 `perPerson`、`total`、场合可见性、跨空间授权和 60 秒采用收据等既有约束；embedding 不可用时仍按既有规则降级到关键词。
- 这条上限约束的是“注入多少线索”，不约束模型自己知道什么，也不等于模型一定会调用检索工具。

## 3. 第三人称人物识别与建档

### 3.1 识别规则

- 人物匹配按稳定 ID、显示名、`surfaces`、别名做精确匹配；先匹配更长名称，避免 `柚子` 命中 `蜂蜜柚子茶` 的内部。
- ASCII 名称检查词边界；单字中文名称检查相邻字符，减少误命中。
- 同一名称对应多个已登记人物时视为歧义，不返回任何人物 ID；不按相似度、不按先到先得猜测。
- 昵称只有“唯一且精确命中”时才识别；仅凭昵称无法确定身份时，应询问稳定账号或请用户补充信息。
- 结构化提及（如 QQ 的 `[CQ:at,qq=...]`）会登记为消息的 `mentions`，指向稳定账号；适配层同步时用宿主提供的发送者 ID 和名称登记实体，不从聊天文本猜身份。

### 3.2 A 谈 B，B 不必发言

- 自动召回和人物检索都会从当前 query、结构化提及、最近消息中解析被谈到的 B，即使 B 在该场合没有发过言，也可以建立/读取 B 的档案。
- 整理提示词会带上允许的 actorId、人物名称对应表和结构化提及，明确“说话人不等于被描述的人”；A 明确介绍 B 时，目标人物是 B，不是 A。
- 提示词要求只提问、猜测、玩笑或否认不产生肯定档案；这是模型行为约束，不是代码层的确定性事实校验，整理模型仍可能误写，需要人工核对。

### 3.3 转述来源

- B 的档案来源引用会携带 `reporterId`（转述者 A）、`aboutActorId`（被描述的 B）和 `attribution`（`self-report` / `third-party` / `window-context`）。
- A 谈 B 时写入的条目通常是 `third-party`；同一场合内召回文本带 `【含他人转述】`，字段级 `sourceRefs` 保留 A 的原话来源。
- 这类内容不得当成 B 自述，也不得因为写进了 B 的档案就改变原始证据归属。

## 4. 跨渠道与场合边界

- 跨渠道不开放原话：即使读取到其他场合的档案摘要，返回的 profile `sourceRefs` 也只保留当前 chatKey（或同场合人工来源）的引用；其他场合的消息、历史和原话不随摘要外带。
- 独立协议的新空间默认 `same-scope`。只有管理员在设置中显式保存了 `profileCrossScope` 或 `profilePolicy`，才按既有档案共享策略（`same-scope` / `group-peers` / `all`）读取其他场合的档案。
- 旧协议继续按实例已有的 `profileCrossScope`、`profilePolicy` 和策略基线执行；本次不改变现场配置，不把旧协议自动切成新协议。
- 不能承诺“任意跨渠道都可查”。可查范围取决于空间授权、场合策略和管理员显式配置；原话始终受场合限制。

## 5. QQ 适配层

- 旧协议：自动注入传 `purpose:"automatic"`；`memory-vec__search` 传 `purpose:"query"`，先查人物档案与人物层，没有再走语义检索；可选 `userId` 指向被查询人物。
- 独立协议：自动召回传 `purpose:"automatic"`；`search` 传 `purpose:"query"`，有 `userId` 时作为 `actorIds` 传入；`search` 的原话检索固定当前场合，不接受跨场合 `chatKey`；人物档案共享仍由服务设置决定。
- 两种协议的提示词都补充了第三人称场景：谈到 B、需要评价/介绍 B，或上下文只有一两条零碎印象时，先主动查“人物名 + 具体话题”；`remember` 的 `userId` 明确为“被描述的人”，不是固定当前说话人。
- 生产基础配置本次不动，仍可按旧协议运行；是否切到独立协议是单独的部署/验证决定，本补丁不切换配置。

## 6. 验证边界

- 本机验证：独立服务测试 34 项、QQ 适配器测试 15 项全部通过，HTTP 用例已启用；原开发树完整回归 432 项全部通过。这些测试有重叠，不相加作为独立用例数。

- 本次没有实际 QQ 对话实测，不能声称模型在真实会话中一定会调用 `memory-vec__search` 或 `remember`。
- 提示词和工具描述改善的是“模型知道该在什么场景查/记”；工具契约测试验证的是“模型调用后工具如何处理第三人称”，两者不是一回事。
- 仓库中相关测试覆盖了：B 未发言时按唯一别名召回、长名/歧义/ASCII 边界、整理阶段 A 谈 B 并保留转述来源、适配层登记宿主发送者与结构化提及；设置 `VEC_MEMORY_ROOT` 时还包括真实 HTTP 下的第三人称注入与写入。还覆盖关键词字段排序、整个自动请求最多两条、共享空间合并后的总限额、跨渠道授权与原话边界、旧协议人物工具查询。
- 仍未验证：真实 QQ 群聊中的工具调用率、真实昵称歧义分布、真实跨渠道数据的共享效果、模型对提示词的理解稳定性。
