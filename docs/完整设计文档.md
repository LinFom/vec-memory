# vec-memory 完整设计文档

- 文档日期：2026-11-05
- 目标版本：0.33.1
- 适用对象：接入者、部署者、维护者、评审者
- 代码基线：本仓库当前源码与测试；不是对某个已发布产物的宣传页

> 本文只写源码、测试和仓库内评估文件能支持的内容。目标与实现不一致的地方会直接标成“差距”，不把计划写成已完成。

## 0. 一句话结论

vec-memory 现在是一个用 Node.js 实现的、可独立启动的记忆服务：项目通过 HTTP JSON `/api/v1` 或进程内 `createService(...).handle(...)` 使用同一套业务实现；每个空间由独立 worker 承载，默认不自动调用生成模型，记忆以证据、人工修订和可追溯日志为中心。

它仍然是个人自托管项目，不是成熟的 SaaS，也没有经过生产级全量验证。0.32.0 的重点是：独立服务认证、场景档案、人工纠正、账号绑定、分层检索与降级、可续跑的向量重建、加密备份与旁置恢复；不是重写成数据库，也不是重写 Python。0.32.1 是在该基线上的补丁：收紧自动人物印象、补齐第三人称提及与转述来源，并改进 QQ 适配层的提示词和搜索入口，不改变上述服务与存储基线。

## 1. 版本与旧叙述更正

### 1.1 版本状态

- 目标版本为 `0.32.1`（0.32.0 的补丁）。`GET /api/v1/version` 的 `implementationVersion` 读取 `package.json`，不另设版本常量。
- 包与适配器版本统一为 `0.32.1`。
- 本文件中的“0.32.0”保留为基线版本语义；“0.32.1”指本次第三人称人物回忆与自动印象线索补丁。具体发布以实际打包和测试结果为准。

### 1.2 0.30 叙述中已经不适用的部分

以下旧说法不应再用于描述当前独立服务：

1. **“没有认证”不成立。** 当前所有 `/api/v1` 路由（包括版本发现）都要求 `Authorization: Bearer <token>`；管理接口要求管理员凭据。只有 `/health` 和静态管理页不要求 Bearer。
2. **“必须绑定 QQ-Agent 宿主目录才能用”不成立。** 独立服务通过 `tools/standalone-server.mjs init|serve --root` 初始化并启动；项目、空间和凭据都由服务自己管理。旧宿主格式只保留兼容读取和显式导入。
3. **“消息只能从宿主存档读”不成立。** 接入方可以直接 `POST /messages`，用稳定 ID 提交消息；服务把原料持久化到空间自己的 `input/messages.jsonl`。
4. **“没有权限隔离”不成立。** 空间有 owner 和 readers；项目凭据默认只能访问自己的空间，共享读取必须显式授权并在检索/采用时复核。

但仍然不能反过来说“已经完全脱离宿主”：worker 仍保留 `legacy/data` 兼容目录，QQ 适配层还有宿主数据目录和旧 `/api/vec` 兼容路径，适配层默认端口也与服务默认端口不一致。详见第 14 节和《项目客观评估》。

## 2. 总体架构

### 2.1 进程结构

```text
接入方 / 管理页
      │  HTTP JSON /api/v1
      ▼
src/standalone/server.mjs       HTTP 解析、同源检查、正文大小限制
      │
      ▼
src/standalone/service.mjs      认证、空间权限、管理接口、任务调度、备份/导入
      │  worker_threads
      ▼
src/standalone/worker.mjs       单空间业务：消息、事实、事件、主体、场景、检索
      │
      ├─ src/core/*               现有记忆引擎（事实、事件、向量、归一化、检索）
      └─ 空间目录                  input/、legacy/data/、settings.json、state.json
```

- Node.js 要求：`>=22.5`。
- 每个空间一个 worker 线程；空间内操作由 `service.mjs` 的 per-space 队列和 worker 的消息链串行化。
- 服务根目录有 `.service.lock`，同一数据根只允许一个服务进程持有。
- 公开路径和进程内路径不是两套业务代码：`server.mjs` 解析 HTTP 后调用 `service.handle(...)`；测试和工具也可以直接调用同一个 `handle`。这正是“公开 HTTP JSON `/api/v1` 与进程内同实现”的含义。

### 2.2 为什么保留 Node.js 和现有引擎

- 现有事实槽、事件整理、向量代、归一化、注入排序都在 `src/core/`，已经有大量行为约束和测试。
- 本次按事务边界增加模块（`standalone/`、`scene-memory`、`manual-revisions`、`backup`、`vector-generation`），没有重写 Python，也没有换语言。
- 不新增 MCP 记忆传输。当前对外契约是 HTTP JSON；适配层也是 HTTP。没有“MCP 记忆服务器”这一层。

### 2.3 空间目录布局（理解用，不是稳定磁盘 API）

```text
<service-root>/
  access.json                 管理员/项目凭据哈希、空间 owner/readers
  .service.lock               单进程锁
  backups/                    在线备份文件（备份时跳过）
  spaces/<spaceId>/
    settings.json             模型端点、模型名、开关等
    state.json                后台任务、采用收据
    input/
      source.json             规范原料标记
      messages.jsonl          消息日志（只追加）
      entities.json           实体/别名登记
      memory-operations.jsonl 显式记忆、发现、主体修订的幂等操作日志
      correction-intents.jsonl 人物修订的持久意图
      workspace.jsonl         场景、场景条目、账号绑定
    legacy/data/              现有引擎的库目录（兼容命名）
      memory-vec/
        normalizer/secret.key 占位符身份密钥
        ...                   事实槽、事件、主体、向量代、manual 修订等
```

磁盘布局不是接入契约；升级或迁移时应使用备份/导出工具，不要手工拼接文件。

## 3. 独立服务、权限与隔离

### 3.1 初始化与凭据

初始化：

```powershell
node tools/standalone-server.mjs init --root E:\vec-memory-data
node tools/standalone-server.mjs serve --root E:\vec-memory-data --host 127.0.0.1 --port 8091
```

`init` 生成一次性管理员明文 token，只在输出中出现一次；`access.json` 只保存 `adminHash = sha256(token)`。项目 token 同样只在创建时返回一次，保存的是哈希。

### 3.2 角色

| 角色 | 能力 |
|---|---|
| 管理员 | 所有空间的管理接口、创建项目/空间、设置 readers、查看空间状态、场景管理、账号绑定、备份/导入 |
| 空间 owner | 自己空间的读写、替换 readers、提交消息/记忆/任务/采用 |
| 空间 reader | 只读：recall、status、subjects 读取、people 读取等；不能写消息、记忆、采用或 readers；任务的查询与提交均只允许 owner/admin |
| 非成员项目 | 除 `/health` 外无访问权；共享空间也必须在 `sharedSpaceIds` 中显式请求 |

`permit()` 的判断顺序是：管理员放行；owner 放行；只读请求且项目在 `readers` 中放行；否则 403。空间不存在返回 404。

### 3.3 路由级限制

- `workspace` 的 `state`、`scene`、`link`、`retract`、`preview` 只允许管理员；拥有写权限的项目可用 ensureScene 建立当前场合场景并提交有证据观察；跨渠道提交候选，也可查询和 support。
- 场景条目的 `shareable` 和 `confirm` 只有管理员能设置；普通项目提交外部补充只能得到候选。
- `people` 的 `revision` 需要写权限，且 worker 内再次要求管理员；`preview` 也要求管理员。
- `readers` 只有 owner 或管理员能替换；reader 不能转授权。
- `recall` 会先对请求空间和每个 `sharedSpaceIds` 做权限检查；在每个来源空间上执行时把 `sharedSpaceIds` 清空，避免二次扩散。
- `adoptions` 绑定收据所属项目；采用时重新读取 `access.json` 并复核每个来源空间权限，授权在检索途中被撤销会失败。

### 3.4 隔离边界

- **空间隔离**：事实、消息、事件、场景、账号绑定、向量、设置、任务、收据都在空间目录下；不同空间不共享这些文件。
- **项目隔离**：项目 token 属于一个项目；默认只能进入 owner 空间。共享读取是显式 readers 名单，不会把写权限一并给出。
- **场合隔离**：记忆读取按 `scope`（当前实现只有 `private`/`group` 两种 kind，详见 6.5）过滤；跨空间授权不会自动扩大场合可见性。
- **检索隔离**：共享空间的结果按条返回，来源空间重新标记 `id` 前缀；采用时仍回到来源空间的 worker 记账。

### 3.5 认证的现状和不足

已有：Bearer 认证、哈希存储、管理员/owner/reader 区分、同源浏览器检查、CSP、请求体大小限制、备份加密。

尚未内置：TLS 终止、登录限速/暴力破解防护、token 轮换/吊销接口、管理员操作审计日志、按 IP 的访问控制。远程部署必须放在 HTTPS 反向代理后；管理员 token 不要分发给接入项目。

## 4. 模型费用默认关闭

### 4.1 默认值

`src/core/backend.mjs` 的 `DEFAULT_SETTINGS` 中：

- `autoIndexEnabled: false`
- `autoIndexIntervalMin: 0`
- `consolidateEnabled: false`
- `consolidateIntervalMin: 0`

也就是说，安装/初始化后不会因为“有消息”而自动整理或自动建索引。要产生整理/索引的生成调用，必须显式提交 `POST /jobs`，或在设置中把对应开关设为 `true`。worker 的自动检查间隔最低 60 秒；空间 worker 第一次被调用时才启动。

### 4.2 哪些操作会调用模型

| 操作 | 是否调用模型 | 说明 |
|---|---|---|
| `POST /messages` | 否 | 只做校验和持久化 |
| `POST /memories` | 否 | 归一化/规则处理，不调用生成模型 |
| `POST /discoveries` | 否 | 只核对证据并写主体观察 |
| `POST /jobs {type:"consolidate"}` | 是（LLM） | 未配置 `llmBaseURL`/`llmModel` 会失败为 `LLM_UNCONFIGURED` |
| `POST /jobs {type:"index"}` | 是（embedding） | 未配置 embedding 会失败为 `EMBED_UNCONFIGURED` |
| `POST /recall` 且带 query | 可能（embedding） | 配置了 embedding 时会对查询和候选行做向量化；失败降级到 keyword |
| 自动后台任务 | 仅开关为 true 时 | 默认关闭；恢复备份后也会被强制关闭 |

### 4.3 费用边界

- “默认关闭”关闭的是自动生成/整理，不是“任何请求都不花钱”。如果管理员配置了 embedding，带 query 的 recall 仍可能调用 embedding 端点。
- 设置读取接口只返回非密钥值，密钥只返回“是否已配置”的布尔值；`PUT` 时空字符串表示保留旧密钥，`null` 表示删除。
- 备份恢复后，所有空间的 `autoIndexEnabled`/`consolidateEnabled` 会被设为 `false`；恢复不会自动开始花钱。

## 5. 记忆模型：消息、事实、事件、主体、场景

### 5.1 消息（raw）

`POST /api/v1/spaces/{spaceId}/messages`：

```json
{
  "messages": [{
    "messageId": "m-001",
    "conversationId": "chat-a",
    "actorId": "user-a",
    "role": "user",
    "timestamp": "2026-11-01T08:00:00Z",
    "text": "我喜欢不加糖的茶。",
    "scope": {"kind": "private", "id": "chat-a"}
  }]
}
```

- 每批最多 500 条；单条 text 最多 100000 字符。
- `messageId` 是调用方稳定 ID；同 ID 同内容为 `duplicate`，同 ID 不同内容为 `conflict`。
- 消息日志是只追加的 `input/messages.jsonl`；逐条结果不会因为同批其他条失败而回滚。
- 机器角色（assistant/system/tool）也保留为原始上下文，但不能作为非人工事实的证据；自动整理只消费 user 证据。

### 5.2 事实（facts）

`POST /memories` 写入人物/场合事实槽。关键规则：

- `actorId` 必须先登记为实体。
- `source` 为 `manual`/`assistant`/`evidence`，默认 `assistant`。
- 非 manual 来源必须有同场合、已接收的 user 消息作为 `evidenceIds`；assistant/system/tool 单独不能支撑事实。
- `manual` 可以没有聊天证据，但会写入一条 `type:"manual"` 的来源引用。
- `trait` 必须带 `attr` 或 `itemKey`；`pattern` 被拒绝。
- 相同 `operationId` 重放返回原结果；同 ID 不同请求返回 409 `OPERATION_CONFLICT`。
- 事实记录带 `provenance`、`evidence_n`、`caliber` 等字段；这些是展示和排序依据，不是“客观真理”证明。

### 5.3 事件（events）与长期语料

- 自动整理（显式 `consolidate` 任务）把 user 证据窗口整理为事件，写事件账本和短期层。
- 事件可以有 `hits`（排练/采用计数）、`promotedAt`（升为长期）、`retiredAt`（回收）。
- 长期检索还使用向量语料；`index` 任务把语料嵌入到向量代。
- 事件整理和索引都依赖模型配置；默认不自动执行。

### 5.4 主体（subjects，新事物）

- `POST /discoveries` 记录新梗、术语、作品、项目、物件等主体，不调用模型。
- 只有名称、没有解释时记录 `mention` 候选；有明确解释/用法时记录 `definition`/`usage`。
- 观察带 `knowledgeStatus`（如 `candidate`/`observed`）、`authority`（`automatic`/`manual`）、来源和原话。
- 同一主体下不同说法可以并存；召回用 `【待确认】`、`【人工修订】`、`【存在不同说法】` 等标记。
- 人工纠正/撤回保留原观察、原证据和历史；`expectedRev` 过期返回 409。

### 5.5 场景（scenes）

场景是“群、频道、游戏房间”等长期场合档案，不等同于一条消息或一个事实槽。

- `sceneId` 是稳定 ID；`bindings` 是一组场合键（当前底层只接受 `private`/`group`）。
- `type` 是自由字符串，默认 `channel`；频道/游戏房间在数据层用 `group` scope 承载，靠 `type` 和 `name` 表达语义。这是当前实现的边界，不是已经支持任意 `scope.kind`。
- 条目字段包括：`kind`、`text`、`status`（candidate/observed/confirmed/retracted）、`shareable`、`sourceScope`、`evidence`、`authority`、`derivedFrom`、`history`、`legacyRecord`。
- 同场景同 `kind` 同规范化文本视为同一内容：不新增条目；如果带来新的证据，只合并证据，不增加“真理分数”。
- 不同文本（包括相互冲突的说法）可以并存；不会因为语义相似自动合并。

### 5.6 五层之间的关系

```text
消息（raw，含机器上下文）
  ├─ 事实（人物/场合槽，人工修订覆盖）
  ├─ 事件（整理产物，短/长期）
  ├─ 主体（新事物观察，候选/人工/冲突）
  ├─ 场景（群/频道/房间的长期档案，逐条可共享）
  └─ 工作记忆（最近消息，仅当前会话/场合）
```

证据是跨层连接：事实有 `provenance`，事件有窗口引用，主体观察有原话引用，场景条目有 `evidence` 和 `derivedFrom`。但“有证据”只表示来源可追溯，不表示内容正确。

## 6. 来源、证据与人工纠正

### 6.1 来源等级

- `manual`：管理员/人工显式写入，可以不附聊天原话。
- `assistant`/`evidence`：必须有同场合、已接收的 user 消息。
- 自动整理产生的事实/事件是机器产物；它们可以进入候选或观察层，但不能覆盖人工结论。
- 旧 `group-memory` 导入的记录保留 `legacyRecord` 和 `legacy:true`，并保持未核验状态；旧 `hits` 不参与新场景条目的可信度计算。

### 6.2 人物人工覆盖不被机器重写

`ManualRevisions` 把人工新增和修订放在独立日志 `manual/revisions.jsonl`：

- `addition`：人工新增一个属性/事项；它和机器槽共用规范 key，但有自己的 `itemProvenance`。
- `revision`：`replace`/`hide`/`restore`，带 `expectedEtag` 和 `baseFingerprint`。
- `records()` 把机器槽和人工新增合并；`project()` 把人工修订投影成读模型；`readStore()` 用 Proxy 暴露只读槽，拒绝 `put`/`reset` 等写操作。
- 机器再次抽取同一槽时，投影仍显示人工值；如果底层机器内容变了，条目标记 `sourceState: "source_changed"`，但不会静默覆盖人工值。
- 同名事项人工新增会返回 `ITEM_EXISTS`，要求编辑已有项或换名，避免重复堆叠。

测试 `test/standalone-upgrade.mjs` 中“人物纠正后再用旧证据重抽”验证了人工值在重启后仍为人工值。

### 6.3 场景条目的重复、撤回、恢复

- **重复**：同场景、同 kind、同规范化文本 → 返回 `duplicate:true`；证据按 `(chatKey,id)` 去重合并；不新增条目，不把重复当可信度。
- **撤回**：管理员先 `preview(entryId)`，拿到 `previewToken`；`retract` 校验 token 后，把 `proven` 集合中的条目逐个改为 `retracted`，写历史，并把签名加入 `rejectedSignatures`。
- **墓碑**：之后用同一文本重新提交（不带 `entryId`）会被 `blocked:true` 挡住，避免“撤回后又被自动长回来”。
- **显式恢复**：管理员带 `entryId`、`expectedRev`、`previewToken` 再提交一次，可以恢复该条；历史保留。当前测试覆盖了撤回、墓碑和依赖联动，未覆盖管理页恢复的完整端到端流程，验收时应单独演练。
- **历史**：每次变更把旧版本压入 `history`（去掉嵌套 history）；不会物理删除。

### 6.4 依赖联动与“待核对”

`preview(entryId)` 返回：

- `proven`：该条自身 + 传递 `derivedFrom` 依赖（明确依赖）。
- `suspected`：仅因共用证据而被怀疑相关的条目。

撤回/纠正只自动处理 `proven`；`suspected` 只提示人工核对，不会因为“语义相似”批量修改。依赖环会被拒绝；已撤回或不存在的依赖返回 `INVALID_DEPENDENCY`。如果历史依赖记录已经缺失，系统无法凭现有状态自动还原，必须人工处理。

### 6.5 人物纠正到场景：durable intent

人物条目的修订可能影响引用它的场景条目。实现不是“多文件原子提交”，而是：

1. 管理员先 `people action:"preview"`，得到人物 item、`previewToken` 和受影响场景条目。
2. `action:"revision"` 校验 `expectedEtag` 和 preview token；先把修订意图追加到 `input/correction-intents.jsonl`，再执行。
3. 每次 worker 处理请求前运行 `recoverCorrections()`：对每条意图，先 `manual.commit`（幂等），再按 preview token 撤回依赖场景条目。
4. 修订完成后清空 worker 内存里的采用收据，避免用旧内容继续确认采用。

这意味着：

- 崩溃后下一次请求会补齐未完成的意图；但**不是**两个文件同时成功/同时失败的原子事务。
- 中途崩溃可能短暂出现“人物已改、场景未撤”的状态；下次请求会修复。
- 如果意图日志本身损坏，服务会进入只读/不可用，而不是猜测修复。
- 没有历史依赖记录时，不能自动重建受影响的场景。

## 7. 账号绑定

`workspace` 的 `link` 动作：

```json
{
  "action": "link",
  "operationId": "bind-1",
  "a": "qq:10001",
  "b": "game:10001",
  "confirmed": true
}
```

规则：

- `a !== b`；两个账号必须已登记为实体；worker 会把平台账号解析到规范 ID。
- 必须 `confirmed:true`，否则 `CONFIRMATION_REQUIRED`。
- 只有管理员能绑定/解绑。
- 解绑用同一条 `link` 记录，`active:false`，并要求 `expectedRev`；不删除原记录。
- 绑定是**读时投影**：`accounts(account)` 做传递闭包，返回同一人的账号集合；不改写实体 ID、不合并事实文件、不迁移消息。
- 人物读取只用这些账号去匹配同一 `scope` 下的人工/机器槽；不会因为绑定而让 A 场合的原话出现在 B 场合。
- 绑定不会放大空间权限；空间 readers/owner 仍按原规则判断。

当前限制：绑定后“任意场合人物原话自动互通”不成立。项目调用与自动注入仍按当前 `scope` 过滤；管理员可在管理页显式使用 `allScopes:true` 汇总已绑定账号的各场合印象，逐项保留账号与场合来源；跨场合仍受场合策略和可见性限制。绑定只解决“同一人在不同平台的稳定账号如何一起找”，不是全局身份合并。

## 8. 分层检索与真实降级

### 8.1 召回层

`POST /recall` 返回的 `items.layer` 可能是：

| layer | 来源 | 说明 |
|---|---|---|
| `working` | 当前场合最近消息 | 最多 6 条；按 `conversationId` 可收窄 |
| `episodic` | 近期事件 | 未升长期的事件 |
| `long-term` | 长期事件/语料文档 | 事件或语料检索命中 |
| `semantic` | 事实槽 | 含人工投影；每行带来源 |
| `profile` | 人物档案 | 默认同 scope；明确开启档案共享后按策略读取；主动查询合并 trait，自动模式逐字段 |
| `subject` | 新事物观察 | 候选/人工/冲突标记 |
| `scene` | 场景条目 | 当前场景或显式 sceneId；共享条目证据不外带 |

`purpose:"automatic"` 时，上表的 `semantic` 与 `profile` 只保留合计最多 2 条字段级关键词线索；其他 layer 不受这 2 条上限约束。`purpose:"query"` 仍走完整召回。

### 8.2 检索流程（简化）

1. 归一化 query 和当前场合。
2. 收集当前 scope 的事实槽和人物候选；如果 query 非空且有候选：
   - 检查 embedding 端点；
   - 查询向量 + 候选行向量，算 cosine；
   - 失败或未配置 → keyword 相似度。
3. 用 `selectInjectLines` 选行：query 时 `mode:"hard"`，无 query 时 `mode:"boost"`；每人物上限 2，总上限 8。
4. 叠加 profile、事件、主体、工作记忆、场景；按 `id` 去重。
5. 如果 query 非空，再走语料/事件检索（`/search`），可能返回 `vector`/`hybrid`/`keyword`。
6. 生成 `receiptId`，保存条目集合和来源；60 秒内可确认采用。

`purpose:"automatic"` 不走向量人物分支，按 8.6 只保留人物关键词线索；上面的完整流程用于 `query` 等显式检索。

### 8.3 降级不是“静默返回空”

- embedding 未配置：worker 内部 `degraded.code = "EMBED_UNCONFIGURED"`，事实候选改用 keyword。
- embedding 调用失败：worker 内部 `degraded.code = "EMBED_FAILED"`，保留原因，改用 keyword。
- 语料/事件检索失败：显式抛出错误码，不伪造成功。
- 服务层 `/api/v1/spaces/{spaceId}/recall` 返回按来源空间汇总的 `actualMode` 和 `degraded`，公开报告未配置或调用失败等降级原因。
- `selectInjectLines` 的 `hard` 在没有相似度信息（`sims=null`）时会降级为 `boost`；但 worker 在 query 且候选存在时会先给出 keyword 相似度数组，因此实际走 hard 阈值。这个区别很重要：缺依赖不能变成“什么都不注入”，也不能把“没有信息”伪装成“全都不相关”。

### 8.4 场景自动注入与显式查询

- **自动日常注入**（`recall` 不传 `sceneId`）：只取绑定到当前场合的场景条目；跨渠道 `shareable` 条目不会因为“可共享”就自动进入当前场合。
- **显式 `sceneId`**：读取该场景的条目，并允许逐条 `shareable` 的跨渠道条目进入；但 `sourceRefs` 逐条按证据所属场合过滤，只返回当前 chatKey 的引用，证据和历史不随摘要开放。
- `workspace query` 还会去掉 `history` 和 `legacyRecord`；管理页的 `workspace state` 才能看到完整历史，且要求管理员。

### 8.5 固定六条合成评估与 hard 阈值

`tools/evaluate-memory.mjs` + `test/fixtures/recall-labelled.json` 使用 6 条人工标注的合成查询，只测关键词/语义候选和场合可见性，不调用外部模型。

**before**（`docs/recall-evaluation-before-20261101.json`）：

- `precisionAt8 = 2/3 ≈ 0.667`
- `recallAt8 = 1`
- `falseInjectionRate = 1/6 ≈ 0.167`
- 失败表现：`unrelated` 查询在 boost 模式下仍然召回了“喜欢红茶/喜欢绿茶”两条无关偏好。

**after**（`docs/recall-evaluation-20261101.json`）：

- `precisionAt8 = 1`
- `recallAt8 = 1`
- `falseInjectionRate = 0`
- 做法：query 时使用 `hard` 阈值，低于阈值的候选不注入；`selectInjectLines` 只在有 query 时走 hard。

边界：这只是 6 条合成关键词语义检索的微型验证。它没有验证真实 LLM 抽取质量、讽刺/反语理解、长期记忆的真实优势、跨产品比较，也不能证明生产准确率。before/after 两个 JSON 都保留，不能只引用 after。

### 8.6 第三人称人物与自动线索（0.32.1）

#### 8.6.1 要解决的问题

旧自动注入可能把同一人的多个 `trait` 字段一次铺开，模型看到的是“整卡”而不是当前话题真正需要的一两条线索；人物候选又偏向当前发言者，A 问 B 而 B 没在该场合发过言时，容易漏掉 B 的档案；跨场合档案、转述来源和“B 自述”的边界也不够明确。0.32.1 针对这三点做增量设计，不改变事实、事件、场景和存储模型。

#### 8.6.2 自动注入与显式查询分流

1. **自动注入使用 `purpose:"automatic"`。** QQ 旧协议的 `/api/vec/inject`、独立协议的 `recall` 都显式传这个值；自动注入不再与显式查询共用完整的人物检索路径。
2. **人物层合计最多 2 条。** `src/core/keyword-impressions.mjs` 把事实候选和 profile 字段合并成一个池，分别计算正文与姓名的关键词重合度（正文权重 2，姓名权重 0.25），过滤零命中后按分数和可信度排序，最后截取最多 2 条。这个 2 是“整个自动请求的人物 `semantic` + `profile` 合计”，不是每人 2 条，也不是所有层合计 2 条。
3. **逐字段，不整卡。** profile 以单个 `k=v` 字段为候选；字段级来源优先取 `itemProvenance[itemKey]`。因此两个人或同一人的两个字段可以各占一条，但不会把整张人物卡拼成一条。
4. **只有人物层受限。** 自动分支只替换人物 `semantic`/`profile`，事件、长期语料、主体、工作记忆、场景等其他层仍按既有规则追加。整个注入块的总条数仍可能超过 2 条，这与“人物线索最多 2 条”不矛盾。
5. **自动路径不因人物线索调用 embedding。** 人物层按关键词处理；语料检索在 automatic 下也固定使用关键词；其他层沿用原有规则。显式查询 `purpose:"query"` 不受这 2 条上限约束，仍可走向量/关键词完整召回，但仍受 `perPerson`、`total`、场合可见性、跨空间授权和 60 秒收据等既有约束。

#### 8.6.3 第三人称识别与建档

- `src/core/person-targets.mjs` 的 `mentionedPeople` 只做精确匹配：稳定 ID、显示名、`surfaces`、别名；先占用更长名称，避免 `柚子` 命中 `蜂蜜柚子茶` 的内部；ASCII 名称检查词边界，单字中文名称检查相邻字符。
- 同一名称对应多个已登记人物时返回 `ambiguous`，不返回任何 ID；不按相似度、不按先到先得猜测。昵称只有唯一精确命中时才可用；仅凭昵称无法确定身份时应询问稳定账号。
- 结构化提及（如 `[CQ:at,qq=...]`）进入消息 `mentions`，指向稳定账号；`canonicalVocabulary` 会把提及目标登记进词表。QQ 适配层同步时用宿主提供的发送者 ID/名称登记实体，不从聊天正文推断身份。
- A 谈 B 不要求 B 发言：worker 的人物集合会合并 query 中解析出的 B、最近消息的结构化提及和消息参与者；B 即使没在该场合说过话，也可读取/建立 B 的档案。
- 整理提示词会带允许的 actorId、人物名称对应表和结构化提及，并明确“说话人不等于被描述的人”；只提问、猜测、玩笑或否认不产生肯定档案，A 明确介绍 B 时才把目标指向 B。这些是提示词约束，不是确定性事实校验；整理模型仍可能误写，需要人工核对。

#### 8.6.4 转述来源

`src/core/provenance.mjs` 的引用新增三个可选字段：

- `reporterId`：转述者（例如 A）的稳定 ID；
- `aboutActorId`：被描述者（例如 B）的稳定 ID；
- `attribution`：`self-report`、`third-party` 或 `window-context`。

整理时，如果窗口内所有发言者都不是被描述者，标为 `third-party`；唯一发言者就是本人时标为 `self-report`；多人窗口包含本人时标为 `window-context`。`remember` 写入也按发送者与目标人物是否同一人设置转述来源。人物档案在同一场合召回时，任一来源为 `third-party` 就加“【含他人转述】”，并保留 A 的原话来源；这类内容不得当成 B 自述，也不改变原始证据归属。字段级来源优先使用 `itemProvenance`，避免整条档案共用一份来源。

#### 8.6.5 跨场合边界

- 独立协议新空间默认 `same-scope`：worker 只有在 `settings.json` 显式存在 `profileCrossScope` 或 `profilePolicy` 时，才调用既有策略解析；否则强制同场合。管理员显式保存后才按 `same-scope` / `group-peers` / `all` 的既有规则读取。
- 即使档案摘要跨场合可见，返回的 profile `sourceRefs` 仍只保留当前 chatKey（或同场合人工来源）的引用；其他场合的消息、历史和原话不随摘要外带。
- 旧协议继续按实例已有的 `profileCrossScope`、`profilePolicy` 和策略基线执行；本次不改变现场配置，不把生产从旧协议自动切到独立协议。
- 因此不能承诺“任意跨渠道都可查”：可查范围由空间授权、场合策略和管理员显式配置共同决定，原话始终受场合限制。

#### 8.6.6 验证边界

相关测试包括 `test/standalone-third-person.mjs`（B 未发言按唯一别名召回、长名/歧义/ASCII 边界、整理阶段 A 谈 B 并保留转述来源）和 QQ 适配层的发送者/提及登记、第三人称工具契约测试。本文不预填通过数字；本次没有实际 QQ 对话实测，提示词改善不等于模型一定会调用检索或写入工具，验证结果见补丁说明。

## 9. 采用计数

### 9.1 什么是采用

`POST /adoptions` 只表示“这些条目被放进了模型上下文”，不表示模型真的使用了、理解了或事实正确。

- 服务层收据：绑定目标空间、项目、条目集合、来源空间，60 秒过期；确认时重新校验共享权限。
- worker 收据：绑定本次 recall 的 `itemIds`、事件 ID 集合；确认时只对 `event:` 和 `document:` 条目做排练计数。
- 重复确认同一集合返回 `replayed:true`，不重复累计。
- 事件排练有 30 分钟冷却，避免同一轮重复注入刷计数。
- 服务重启可能丢失 worker 内存收据，导致“少计”；系统不会补造采用次数。
- 采用收据在恢复/导入后会清空；不能拿旧收据继续确认。

### 9.2 采用与“可信度”的区别

- 事实槽的排序可信度是 `evidence_n × legacy 折减`（多值槽另有计价），不是采用次数。
- 采用只影响事件/文档的排练计数，进而影响事件的保留/升长期；它不会直接把一个场景条目变成“正确”。
- 场景重复提交同一内容不增加条目；重复证据不重复计数。
- 这意味着系统仍可能出现“被频繁召回/排练的内容更靠前”的自强化，详见《项目客观评估》E 项。

## 10. 任务与续跑

### 10.1 任务队列

- 任务类型只有 `consolidate` 和 `index`。
- `POST /jobs` 可带 `operationId`；同 ID 不同正文返回 `OPERATION_CONFLICT`。
- 任务状态：`queued` → `running` → `completed`/`failed`；失败带 `{code,message}`。
- 状态写入空间 `state.json`；服务启动时重新调度 `queued`/`running` 任务；失败的任务不会自动重试。
- 每个空间串行执行；`runJob` 在开始和结束都写状态。
- 在线备份/导入期间 `exclusive` 会等待队列、quiesce 并关闭引擎；完成后重开并重新调度 queued 任务。

### 10.2 向量重建的续跑

`src/core/vector-generation.mjs` 解决的是“重建一次要几千次嵌入调用，中断后不能重新花钱”的问题：

- `rebuild-job.json` 固定在库根，记录 `generation`、`encoding`、状态、计数。
- 新代目录在 `vector-generations/<generation>/`；旧代在重建期间设 `writeBarrier`，只读。
- `VecStore.put()` 逐条落盘（bin/meta 追加 + put journal + index 重写），已完成条目在磁盘上可读。
- 可续跑状态：`running`、`paused-quota`、`paused-limit`、`ready`、`failed`；`published` 不再续跑。
- 复用作业时继承 `startedAt`、`total`、`done`、`embedded`、`skippedResume`、`rejected`、`unreadable`、`carried` 等计数；避免“续跑后显示 0”。
- 已存在的条目按 `sourceHash`/`hasTarget` 跳过；同一个被拒 ID 不重复计数。
- `publish()` 原子写 `vector-active.json` 指针；未发布的新代不服务查询。旧代在整个重建期间仍是活动代。
- `prepareVectorGeneration` 在编码身份兼容时直接返回旧 store，不新建代、不花费；不兼容时才建新代。
- 兼容性判断包括 model、dimensions、endpoint、revision、normalizer、documentFraming 六项；旧库缺少记录时是 `unknown`，默认 fail-closed 拦截事件向量搬运，不能把“不知道”写成“兼容”。

### 10.3 不是所有任务都能细粒度续跑

- `index` 有代目录和作业文件，能按已写入条目续跑。
- `consolidate` 由现有整理管线执行，没有与 index 同级的“逐窗口检查点”；中断后按现有整理逻辑重跑，已处理窗口由整理状态/幂等保护，不能宣称为任意步骤可恢复。
- 恢复备份后，queued/running 任务被标记 failed；需要人工复核再重建。

## 11. 备份、导入与恢复（概览）

详细命令和演练步骤见 [备份与恢复操作说明](operations/backup-restore.md)。这里只写设计边界。

### 11.1 两种备份

| 类型 | 内容 | 密码 | 用途 |
|---|---|---|---|
| 完整服务备份 `kind:"service"` | 服务根下的配置、`access.json`（凭据哈希/空间授权）、所有空间、身份密钥、消息/操作日志、向量、场景/账号绑定 | 必须 ≥8 位 | 整机迁移/灾难恢复 |
| 空间备份 `kind:"space"` | 单个 `spaces/<id>`；`settings.json` 去掉 key/token/secret/password 字段；`state.json` 清空 jobs/receipts | 可选；建议设置 | 单空间迁移/复制/导入 |

- 归档是 JSON envelope + gzip；有密码时用 scrypt + AES-256-GCM。
- 未压缩内容上限 512 MiB；不是流式数据库备份，整个归档在内存中构建/校验。
- 备份跳过 `.service.lock`、`backups/`、`*.tmp`；拒绝符号链接和不安全路径。
- 空间备份仍包含该空间的 `normalizer/secret.key`（身份密钥），因为它决定占位符和旧向量文本；所以空间备份也不是“可以随便公开”的文件。

### 11.2 完整恢复

- 只恢复到**新目录**（服务 API 会生成 `root.restore-<uuid>` 旁置目录；CLI 要求目标不存在）。
- 校验归档、密码、逐文件 checksum、JSON/JSONL、日志 hash 链；完整服务还要求 `access.json` 有 `adminHash`。
- 校验后运行 `audit`（每个空间一个 maintenance worker）；失败则保留旁置目录，**不能切换**。
- 恢复会关闭自动模型任务；queued/running 任务标记 `RESTORED_REVIEW_REQUIRED`；receipts 清空。
- 切换是人工动作：停止旧服务，用新目录作为 `--root` 启动；旧目录保留用于回退。

### 11.3 空间导入/替换

- 新空间：目标不存在，导入到 `spaces/<newId>`。
- 替换：`replace:true` 且目标存在；旧目录重命名为 `spaces/<id>.rollback-<uuid>`，新内容 rename 到目标。
- `import-intent.json` 记录 `destination/staging/rollback`，启动时若目标缺失则从 staging 或 rollback 补齐，并重置该空间的 `readers`。
- 替换后 `access.spaces[sid] = {owner, readers: []}`：共享授权重置；账号绑定在 `workspace.jsonl` 中随空间保留；receipts 清空；jobs 为空/需重建。
- 不做自动合并；没有“把两个空间的消息/记忆合并”的接口。

### 11.4 归档上限

- 创建时未压缩总大小 >512 MiB → `BACKUP_TOO_LARGE`。
- 服务上传上限 1 GiB；`inspectBackup` 对超大 envelope 也拒绝。
- 这是为个人自托管设计的有界备份，不是大型流式数据库备份；超大库应使用文件系统快照/分区导出，并自行验证。

## 12. UI 与 QQ 适配

### 12.1 管理页（`web/standalone.html`）

单页管理界面，管理员 token 只保存在页面内存，连接后清空输入框。包含：

- 项目/空间创建，readers 授权；
- 设置读取/保存（密钥不回显）、状态、整理/索引任务、任务进度、检索；
- 人工记忆与实体登记；
- 新事物条目：按场合查询、查看来源/历史、纠正/撤回；
- 人物档案：trait 小卡在前，动态印象在后；修订、预览关联影响、撤回/恢复；
- 账号绑定/解绑；
- 场景：新建/绑定当前场合、候选/确认、shareable、预览、纠正/撤回/恢复、历史；
- 备份：完整/空间导出、上传、下载、预览 checksum、导入/替换。

页面不是多用户后台：没有登录会话、没有项目自助注册、没有审计日志页。`token` 只存在内存；刷新页面后要重新输入。

### 12.2 UI 的已知边界

- 场景“恢复”复用条目编辑路径；完整 UI 恢复流程缺少专门测试。
- 人物 `preview` 与 `revision` 依赖当前页面缓存；切换空间/场合/账号后会要求重新读取，避免旧 etag 误提交。
- 备份导入页把完整恢复和空间导入放在同一区域；完整恢复返回的是旁置目录，不会自动切换启动根。
- 管理页使用管理员 token；项目日常接入应使用项目 token 调 API，不要共用管理员 token。

### 12.3 QQ-Agent 适配

`adapters/qq-agent/index.js` 是薄适配层：

- `protocolV1:true` 时注册 `remember`、`remember_thing`、`remember_scene`、`query_scene`、`search` 等工具；否则走旧路径。
- 旧协议自动注入传 `purpose:"automatic"`；`search` 传 `purpose:"query"`，先查人物档案/人物层，没有再走语义检索；可选 `userId` 指向被查询人物。
- 独立协议自动召回传 `purpose:"automatic"`；`search` 传 `purpose:"query"`，有 `userId` 时作为 `actorIds` 传入，且只查当前场合。
- 两种协议的提示词都补充第三人称场景：谈到 B、评价/介绍 B，或只有一两条零碎印象时先主动查“人物名 + 具体话题”；`remember` 的 `userId` 明确为“被描述的人”，不是固定当前说话人。
- 生产基础配置本次不切换，仍可按旧协议运行；是否切 v1 是单独的部署/验证决定。没有实际 QQ 对话实测，不能声称模型一定会调用工具；提示词改善只说明“模型更可能知道何时查/记”，不证明真实调用率。
- 通过 HTTP 调 `/api/v1/spaces/<space>/...`，需要 `serviceBaseURL`、`spaceId`、`serviceToken`。
- 消息同步由 `protocol-v1.mjs` 的持久队列完成：队列在宿主数据目录，按稳定消息 ID 去重，批量 100，失败保留；目标 base/space 改变会拒绝，要求先完成原目标迁移。
- 写侧另有 `memory-vec-outbox.jsonl` 补发队列（上限 200 条，4xx 丢弃、5xx/网络保留，约 3 分钟重试）；它解决“服务短暂不可用”的写丢失，不是通用消息总线。
- 适配层不调用外部模型；模型调用发生在服务端显式任务/查询中。
- 适配层文件头与清单均标注 0.32.1；默认 `serviceBaseURL` 仍是 `http://127.0.0.1:8088`，而独立服务默认端口是 8091；部署时必须显式对齐端口，否则会“服务在跑但适配层连不上”。

## 13. 存储事务与失败模型

### 13.1 单文件日志：DurableLog

- 每条记录包含 `version/seq/previous/operationId/fingerprint/data/result/hash`；加载时校验序号、前哈希、hash、operationId 唯一。
- 追加前先 `fsync`；写失败会尝试 `ftruncate` 回滚到原长度；回滚失败则标记只读。
- 打开时发现尾行不完整、hash 不匹配或未知记录 → `readOnlyReason`，之后读写都返回 `STORAGE_UNAVAILABLE`。
- `operationId` + 请求 fingerprint 提供幂等重放；同 ID 不同请求 409。
- 这是“单文件追加事务”，不是跨文件事务。

### 13.2 跨文件一致性

写入可能涉及：

- `input/messages.jsonl`
- `input/memory-operations.jsonl`
- `input/correction-intents.jsonl`
- `input/workspace.jsonl`
- `legacy/data/memory-vec/manual/revisions.jsonl`
- `legacy/data/memory-vec/...` 的事实槽/向量
- `state.json` 的任务与收据

这些文件没有数据库级 2PC。系统用以下手段缩小失败窗口：

- `saveJson` 用临时文件 + fsync + rename 原子替换；
- 每个业务日志独立 fsync，并用 operationId 幂等；
- 场景整体状态写在一个 `workspace.jsonl` 提交里；
- 人物→场景用 `correction-intents.jsonl` 持久意图，并在每次请求前恢复；
- 空间导入用 `import-intent.json` 记录两次 rename；
- 向量有 `put-pending.json`、代指针和 `rebuild-job.json`。

仍然存在的窗口：

- 人物修订与场景撤回不是同时提交；崩溃后要等下一次请求/重启恢复。
- 消息已接收但索引/整理未做，是正常状态，不是原子失败。
- 备份在 quiesce 后读取，能避免并发写，但不能修复备份前已经存在的跨文件半完成状态。
- `audit` 能检查日志/存储可读性，不是全量语义校验，不能证明每条记忆都正确。

### 13.3 只读与失败关闭

- 事实库、手动修订、场景、消息日志、主体、lineage 任一不可读 → 503 `STORAGE_UNAVAILABLE`，不返回空结果冒充“没有记忆”。
- 向量模型/维度/编码不匹配 → 明确错误（`MODEL_MISMATCH`/`DIM_MISMATCH`/`ENCODING_MISMATCH`），不混合计算。
- normalizer 密钥丢失且已有映射表 → `SECRET_LOST`，不静默生成新密钥导致所有占位符换号。
- 召回失败不会变成成功：`test/standalone-service.mjs` 验证失败引擎不会产生 `receiptId`，失败 adoption 不会把收据标成已采用。

### 13.4 单写者与锁

- `.service.lock` 记录 pid；启动时若 pid 仍存活则拒绝第二个服务。
- 同一服务根不能被两个进程同时写；没有多主/HA。
- 空间 worker 通过消息链串行；服务层按空间串行；跨空间可以并行。

## 14. 已确认的产品选择与实现差距

以下逐条区分“目标”与“当前代码事实”。

| 产品选择 | 当前实现 | 差距/注意 |
|---|---|---|
| 完整服务密码加密备份，含配置、身份密钥、访问凭据状态 | `createBackup(root,{password})`；`access.json`、`settings.json`、`normalizer/secret.key` 都在归档内；AES-GCM | 备份不恢复明文 token，只恢复哈希状态 |
| 空间备份默认不带模型密钥/服务授权 | 去掉 settings 中 key/token/secret/password 字段；不包含 `access.json`；`state.json` 清空 jobs/receipts | 仍包含 `normalizer/secret.key`；无密码时是未加密 envelope |
| 短暂停写，队列保存待投递消息 | 在线备份 `exclusive` 置 maintenance，新请求 503；QQ 协议队列/outbox 持久保存待投递消息 | 服务端没有通用 HTTP 消息队列；普通客户端收到 503 要自行重试 |
| 完整恢复旁置目录验证后手动停止并切换启动根 | 服务恢复生成 `root.restore-<uuid>`，audit 后返回；不自动切换 | 需要人工停旧、改 `--root`；验证失败目录保留但不能用 |
| 空间导入新空间或显式替换保留 rollback，无自动合并 | staging → validate → `import-intent` → rollback rename；`readers:[]` | 替换后要手工恢复 readers；jobs/receipts 需重建 |
| 恢复自动模型任务暂停 | settings 两个开关设 false；queued/running 标 failed；receipts 清空 | 已完成任务仍是旧状态，不能当新任务依据 |
| 归档有大小上限，不是大型流式数据库备份 | 512 MiB 未压缩上限；上传 1 GiB；全内存 | 大库需文件系统快照/分区方案 |
| 通用场景档案兼容群、频道、游戏房间 | 场景 `type` 自由；底层 `scope.kind` 只有 private/group | 频道/游戏房间用 group scope 承载，不是独立 kind |
| 条目增查改、撤回、显式恢复保留历史 | `workspace` entry/query/retract/preview；history/tombstone | 已验证显式恢复、派生项保持撤回与重启持久化；完整 UI 恢复流程未覆盖 |
| 跨渠道只逐条 shareable，证据/历史不随摘要开放 | query 过滤证据、去 history/legacyRecord；recall 逐条过滤 sourceRefs，仅保留当前场合证据 | 显式 sceneId 可读共享条目，仍受权限/场合 |
| 自动日常注入只当前场景，显式 sceneId 才读共享 | recall 无 sceneId 时按 bindings 过滤；有 sceneId 时允许 shareable | 共享条目可能来自其他 sceneId，这是当前语义 |
| 跨渠道补充候选，管理员确认/目标场景原话支持后升级 | 非管理员只能候选；`support` 要求目标场景 user 原话包含文本 | 需要管理员确认或目标场景明确原话 |
| 相互冲突说法并存 | 场景不同文本并存；主体 `possibleConflict` | 人物事实槽仍按 evidence-max 选行，不保证所有冲突同时展示 |
| 旧 group-memory 显式导入、保留原记录和未核验标志，旧 hits 不作可信度 | `tools/import-group-memory.mjs` 写 `legacy:true`/`legacyRecord`，`confirm:false`；credibility 不读旧 hits | 导入工具默认 8091，可用 VEC_MEMORY_URL 覆盖 |
| 重复同一内容不新增条目，同一证据不重复计数，撤回/纠正留墓碑 | 签名去重、证据按 `(chatKey,id)` 合并、rejectedSignatures/history | 签名是规范化文本，不是语义去重 |
| 人物人工覆盖不被机器重写 | `ManualRevisions.project/readStore`；`source_changed` 标记 | 机器底层仍更新，投影优先人工；不是阻止所有写入 |
| 明确 derivedFrom 依赖可预览联动撤回；仅共用证据算待核对 | `preview.proven/suspected`；只撤 proven | 语义相似不自动改；历史缺失依赖无法还原 |
| 人物到场景纠正用 durable intent 恢复补齐，不宣称多文件原子 | `correction-intents.jsonl` + `recoverCorrections` | 不是 2PC；崩溃窗口存在 |
| 蜂蜜柚子茶/柚子：独立名字可分，旧别名撞名先到者获归属；现在歧义中性替换，稳定 ID 独立 | normalizer v3 的 `ambiguous` 列表；`_resolveTerm` 对歧义返回中性标签；`resolveKnown` 保留稳定 ID | 不声称历史误归属已全部修复；旧向量需检查 |
| normalizer v3 令旧向量需兼容性检查，不自动花钱重建 | `encodingIdentity` 含 `NORMALIZER_VERSION`；`assertQueryCompatibility` 抛 `ENCODING_MISMATCH`；重建只在显式 index 时准备 | 不会自动重建，也不会自动修复旧文本归属 |
| 跨平台管理员确认绑定/解绑，读时投影，不放大权限，仍受场合限制 | `SceneMemory.link/accounts`；worker 要求 admin；人物按 scope 过滤 | 绑定后任意场合原话不自动互通 |
| UI trait 小卡前置，动态印象后置；修订/历史、场景、绑定、备份预览 | `profileCards` 先于 `personImpressions`；各区块存在 | 单页管理界面，无多用户会话/审计 |
| 未知来源事件向量第二次搬运仍 unknown，取原 carryIdentity | `planEventCarry` 优先 `carryIdentity`；测试第二次/第三次仍 blocked unknown | 只有显式 `allowUnknown` 才放行，且仍标 unknown |
| 自动人物印象至多 2 条字段级线索，不整卡铺开 | `keywordImpressions`；`purpose:"automatic"` 分支替换人物 `semantic`/`profile` | 只有人物层受限；其他层和整个注入块仍可超过 2 条；不证明模型会用 |
| A 谈 B 不要求 B 发言，昵称只做无歧义精确识别 | `mentionedPeople`；结构化 `mentions`；整理提示词带允许 actorId/名称表 | 歧义名称不返回 ID；仅昵称不确定时应询问，不能模糊匹配 |
| 第三人称档案保留 A 的转述来源，不当 B 自述 | `reporterId`/`aboutActorId`/`attribution`；召回加“【含他人转述】” | 来源是证据归属，不保证内容正确；字段级来源优先 |
| 新空间默认同场合，显式档案共享设置才跨场合 | worker 检查 settings 是否显式含 `profileCrossScope`/`profilePolicy`；profile refs 过滤当前场合 | 旧协议按实例既有策略；不能承诺任意跨渠道可查，原话不开放 |
| 固定 6 条合成评估，hard 阈值改善 | before/after JSON；precision 2/3→1，recall 1，false 1/6→0 | 微型合成，不外推生产/LLM/跨产品 |

## 15. 限制

1. **不是数据库**：单文件日志 + 自定义向量存储，没有 SQL、没有跨文件事务、没有不停写的在线快照；备份使用停写一致副本。
2. **不是高可用服务**：单进程/单写者/单数据根；没有主从、故障转移、在线扩容。
3. **不是成熟 SaaS**：没有内置 TLS、限速、租户计费、token 轮换、审计导出、SLA。
4. **不是大库备份工具**：512 MiB 上限、内存构建、无增量/流式。
5. **不是语义真理机**：证据可追溯不等于内容正确；采用不等于模型使用；排序可能自强化。
6. **不是全自动身份合并**：账号绑定是读时投影；人物事实仍受场合过滤；历史误归属不会自动修复。
7. **不是任意 scope 模型**：底层只有 `private`/`group`；频道/游戏房间靠 `group` + `type`。
8. **不是完整 v1 客户端生态**：管理页是管理员单页；QQ 适配层默认端口/版本标签需手工对齐。
9. **没有 MCP 记忆传输**：不要按 MCP server 接入；当前契约是 HTTP JSON `/api/v1`。
10. **没有生产全量验证**：现有测试以临时库、合成数据、模拟模型为主，不能替代真实部署验收。
11. **不是任意跨渠道人物检索**：独立协议新空间默认同场合，只有管理员显式保存档案共享设置才按既有策略读取；原话和外部历史不开放。
12. **没有真实 QQ 对话验证**：提示词改善只说明工具更可能被发现/理解，不能证明模型在真实会话中一定调用工具，也不能给出真实调用率。
